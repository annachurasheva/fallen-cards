## 2. Диагностика бага (note.txt)

| Симптом | Причина |
|---|---|
| `----unit-key=...` не сработал | четыре дефиса вместо двух: скрипт искал `--unit-key=` (два дефиса), фильтр не включался |
| `--input= data\...` обработал всё пространство | пробел после `=`: значение пустое → `path.resolve(ROOT, '')` = корень проекта → рекурсивный сбор всех `*-fallen.csv` |
| Вторая команда дала 0 карточек | фильтр включился, но точное совпадение строк: вариант `скф 57 арт. д-н 83 мсб` не совпал ни с одной строкой CSV |
| «Всего записей: 3235» выглядит правдоподобно | счётчик `stats.persons` увеличивался **до** фильтра |

Дополнительно подтверждено: механизм «совпадение ФИО, но разные id-url» уже
существует в `src/validators/registry.js` (`findNameDuplicates`) и вызывается
через `scripts/check-csv.js` — выдаёт предупреждение «ТРЕБУЕТ ВМЕШАТЕЛЬСТВА
ОПЕРАТОРА» для групп с одинаковым ФИО, но разными `document_id`.

## 3. Изменения в `scripts/generate-cards.js` (v2.1 → v3.0)

### 3.1. Валидация аргументов (фикс бага)
- `--input=` без значения → ошибка с подсказкой;
- `--input=` с несуществующим путём → ошибка;
- `--unit-key=` без значения → ошибка;
- в начале прогона печатается фактический вход: `📂 Вход: файл ... / папка ...`.

### 3.2. Группа ключей `--unit-key` (вариант А)
```bash
node scripts/generate-cards.js --input=... \
  --unit-key=404-00-fallen-cards \
  --unit-key=404-01-fallen-cards \
  --unit-key=404-02-fallen-cards
```
Каждый ключ валидируется по словарю `warunits-fallen-cards.json`.

### 3.3. Frontmatter по образцу `new-csv-to-markdown.mjs`
```yaml
---
title: "Фамилия Имя Отчество"
slug: "bitva-za-krym-1942-<транслит ФИО>-<document_id>"
unit_key:
  - "083-04-fallen-cards"
---
```
- `unit_key` — **массив** (зеркалит JSON-SCHEMA пост-обработки), нижней строкой frontmatter;
- slug — с транслитом ФИО (функция `translit` из образца);
- тело карточки — поля с жирными названиями, выводятся только при наличии значения;
- `cause_of_death` не выводится;
- «Воинская часть» = unit-key (не сырой warunit);
- **«Погиб» убрано** — сайт называется «памяти павших».

### 3.4. Правило «нет unit-key → нет генерации»
Записи без ключа не порождают карточку, а уходят в `unknown-pending.json`
(журнал кандидатов для пополнения словаря).

### 3.5. Реестр slug — `data/summary/slug_registry.txt`
- формат: `document_id → slug → unit_key` (табуляция);
- slug **замораживается** при первом выпуске;
- `unit_key` в реестре дополняется (для будущих перечислений войсковых частей
  по офицерскому составу);
- обновляется только при реальной генерации (не в `--dry-run`).

### 3.6. Статистика прогона
`Всего записей` / `С unit_key` / `Без unit_key (пропущено)` / `Отфильтровано` /
`Создано` / `Пропущено (уже существуют)`.

## 4. ⚠️ Направление: возврат к slug БЕЗ транслита ФИО

Текущий формат slug (v3.0):

```
bitva-za-krym-1942-<транслит ФИО>-<document_id>
```

**Зафиксировано направление на возможный возврат** к генерации slug **без
транслита ФИО**:

```
bitva-za-krym-1942-<источник>-<document_id>
```

Причина: если индекс в поисковиках «полетит не так» (изменение URL-структуры
из-за транслита ФИО, дубли/коллизии транслитерации, переиндексация), возможен
возврат к детерминированному slug на основе `document_id`.

Важно: реестр `data/summary/slug_registry.txt` уже реализован с **заморозкой
slug при первом выпуске** — это позволяет в будущем сменить формат генерации
для новых id, не ломая уже опубликованные URL (старые slug останутся в реестре).
