# Регламент работы оператора, получившего свежие данные

Координата: `mem-2026/fallen-cards` · `docs/OPERATOR-REGULATION.md` · 2026-10-13.
Документ описывает действия оператора при поступлении свежих данных (новые CSV
парсинга OBD/PMN) — от размещения CSV до генерации карточек с ключами.

Действующие регламенты (при расхождении приоритет — здесь и в них):
- `docs/WARUNITS-DICT.md` — регламент словаря warunit (v2, семантические ключи);
- `docs/WORKFLOW-TASK-0022.md` — регламент трио и тестовый регламент;
- `docs/CSV_SCHEMA.md` — схема v03 (24 колонки, UTF-8 без BOM);
- `docs/ARCHITECTURE.md` — роли слоёв и модель ключей.

## 1. Цель

Свежие данные (новые персоны из OBD/PMN) должны попасть в карточки с ключами
`unit_key` без потерь и без искажений. Оператор:

1. размещает CSV в `data/processed/**`;
2. запускает перепись warunit (`build-warunits-dict.js`);
3. просматривает кандидатов и принимает решения по ключам;
4. правит активный словарь `warunits-fallen-cards.md`;
5. синхронизирует MD → JSON (`sync-units-dict.js`);
6. генерирует карточки (`generate-cards.js`) и повторяет до полного покрытия.

## 2. Входные данные

- CSV схемы v03 (`docs/CSV_SCHEMA.md`): 24 фиксированные колонки, UTF-8 **без BOM**,
  пустое значение = пустая строка.
- Имена файлов строго с суффиксами `-fallen.csv` / `-unclassified.csv`
  (например `links_pmn_obd-fallen.csv`). Только такие файлы читает перепись.
- Размещение: `data/processed/<имя_прогона>/` (каталог = имя сессии).

## 3. Порядок работы

### Шаг 1. Размещение CSV

Положить свежие CSV в `data/processed/<имя_прогона>/` с суффиксами
`-fallen` / `-unclassified`. Файлы `-error.csv` и `-repeats.txt` перепись не читает.

### Шаг 2. Перепись warunit

```bash
node scripts/build-warunits-dict.js
```

Скрипт автоматически:

- вызывает `scripts/sync-units-dict.js` (MD → JSON), чтобы JSON-зеркало
  активного словаря было актуально (JSON — SSOT для `generate-cards.js`);
- читает активный словарь `data/dictionaries/warunits-fallen-cards.json`;
- собирает все написания warunit из `data/processed/**/*-fallen.csv`,
  `*-unclassified.csv`;
- разделяет написания на **активные** (вариант есть в словаре) и **кандидатов**
  (в словаре нет);
- активные группирует по семантическому ключу словаря и **пересчитывает частоты**
  по всем CSV (каждое повышение объёма — пересчёт);
- кандидатов группирует по сигнатуре набора чисел, ключ **не выдаёт**
  (`proposed_key: null`, `status: "candidate"`);
- пишет атомарную пару
  `data/dictionaries/proposals/warunits-draft3-<метка>.json/.md`
  (метка одна на прогон; перезапись запрещена).

### Шаг 3. Просмотр кандидатов

Открыть свежий `proposals/warunits-draft3-<метка>.md`, раздел
«Кандидаты на заполнение»: частота, написания, document_id. Это новые написания,
которым оператор должен присвоить ключ или добавить их в существующую группу.

### Шаг 4. Решение оператора

Для каждого кандидата возможны два решения:

1. **Новая группа** — написание относится к подразделению, которого ещё нет
   в словаре. Оператор присваивает семантический ключ по `docs/WARUNITS-DICT.md` §2:
   `<NNN>-00-fallen-cards` (узловая дивизия) или `<NNN>-<MM>-fallen-cards`
   (подразделение, MM — порядковый номер в `## Состав` файла дивизии
   `docs/TEXT/<NNN>-*.md`). Состав не подтверждён — ключ `— (оператор)`.
2. **Пополнение вариантов** — написание относится к уже существующей группе.
   Оператор добавляет его в список написаний этой группы.

Ключи выдаёт **только оператор**. Скрипты ключи кандидатам не присваивают.

### Шаг 5. Правка активного словаря

Правится `data/dictionaries/warunits-fallen-cards.md` (четыре колонки:
ключ, развёрнутое имя, написания, адрес источника решений).

- Развёрнутое имя — только из `docs/TEXT/*.md`; нет подтверждения — `— (оператор)`.
- Написания — буквально, через «; », без нормализаций.
- Колонка «Ключ» строго уникальна; строки `— (оператор)` собираются в конец.
- Таблица сортируется по возрастанию колонки «Ключ».

### Шаг 6. Синхронизация MD → JSON

```bash
node scripts/sync-units-dict.js
```

Единственный легальный путь MD → JSON. Ручная правка
`warunits-fallen-cards.json` запрещена (A2, §5.6).

### Шаг 7. Генерация карточек (проверка)

```bash
node scripts/generate-cards.js --dry-run
```

Проверить: сколько персон получили `unit_key`, сколько остались без ключа
(`unit_key: null`). Карточки с ключом не меняются при повторной генерации
(slug детерминированный, без ФИО).

### Шаг 8. Контроль и повтор

Пока есть персоны без ключа — вернуться к Шагу 3: просмотреть кандидатов,
принять решения, поправить словарь, синхронизировать, перегенерировать.
Цикл повторяется до полного покрытия.

## 4. Обязательные правила

- **Никаких нормализаций** строк ЦАМО: без `toLowerCase`, `trim`, `replace`,
  схлопывания пробелов. Совпадение — только точное равенство по знакам (A1, §5.1).
- **JSON — SSOT** для `generate-cards.js`; MD — операторский слой; путь MD → JSON
  только через `sync-units-dict.js` (A2, §3.5, §5.6).
- **Ключи выдаёт только оператор.** Группы `— (оператор)` в индекс не попадают;
  скрипты не создают группы и не выдают ключи сами (§5.3).
- **Частота** — количество уникальных `document_id` (A5).
- **Перезапись запрещена**: `warunits-draft3-*` не изменяются и не удаляются;
  новый прогон — новая пара файлов.
- **CSV v03**: 24 колонки, UTF-8 без BOM, пусто = пустая строка.
- Перед коммитом — `node scripts/clean-dictionaries.js` (регламент очистки,
  `docs/WARUNITS-DICT.md` §5).

## 5. Запреты

- Ручная правка `warunits-fallen-cards.json` в обход `sync-units-dict.js`.
- Нормализация строк данных ЦАМО в любом скрипте конвейера.
- Выдача ключей кандидатам скриптами (ключ — решение оператора).
- Перезапись/удаление исторических пар `warunits-draft3-*`.
- Изменение имён карточек и slug (`docs/ARCHITECTURE.md` §5).

## 6. Тестовый регламент

При проверке изменений словаря и генератора действует тестовый регламент
`docs/WORKFLOW-TASK-0022.md` и аддендумы: 8 стадий + аддендум (тестовые ключи
`999-XX`, sync, rollback). Тестовые ключи `999-XX` в активный словарь
`warunits-fallen-cards.md` не попадают.

## 7. Известные ограничения

- `scripts/build-warunits-table.js` ищет draft3-json в `data/dictionaries/`,
  а перепись пишет в `data/dictionaries/proposals/`. При механической сборке
  активного словаря указывайте свежий файл из `proposals/` явно.
- Журнал ожидающих решения кандидатов (`unknown-pending.json`) ведётся
  оператором; на текущий момент кандидаты видны в блоке `candidates`
  свежего draft3-json/md.
