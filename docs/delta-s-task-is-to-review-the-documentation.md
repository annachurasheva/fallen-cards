Поэтому OG-карточка ведёт именем и отчеством, а не шифрограммой и не артикулом. Не архивная бухгалтерия — мост. ## 2. Модель ключей — моя карта исправлена

Я неверно читал поток: считал, что fallen-cards производит карточки с нормализованными значениями, а Astro их просто рендерит. Вы описываете другую архитектуру, и она правильная:

```
fallen-cards (здесь)
  ↓
  данные павших (CSV)
  + карточки с КЛЮЧАМИ в frontmatter
  ↓
Astro-генератор (mem-2026-soursecraft-site)
  ↓
  словари (units_dict, locations_dict, ranks_dict, burials_*)
  + логика раскрытия ключей → полные значения
  + SCHEMA карточки по ключам
  ↓
  статика → прод
```

Что это значит в работе:

- **Карточка из fallen-cards** содержит ключи, например:
  ```yaml
  title: "Самошвили Резо Цуцкович"
  slug: "bitva-za-krym-1942-1161514741"
  unit_key: "unit-655-sp-404-sd"
  location_key: "loc-duscheti"
  burial_current_key: "burial-hafuz-66-3"
  rebural_from_key: "loc-dalnie-kamyshi"
  published: 2026-10-06
  ```
- **Astro-генератор** при сборке берёт `unit-655-sp-404-sd` из units_registry и раскрывает в полное наименование + краткий боевой путь из history_note; берёт `loc-duscheti` из locations_dict и даёт современное название; и так далее.
- **Пополнение словарей** (набили библиотеку 655-го сп, добавили локацию) → перегенерация статики → выгрузка. Карточки в fallen-cards не меняются: ключ тот же.

Это снимает противоречие, которое меня путало: словарь живёт там, где его запрашивают — **в Astro-репо**, потому что запросы идут от генератора, а не от fallen-cards. fallen-cards — поставщик ключей.

## 4. Следствия для TASK-0014 и слоя подготовки

**Слой подготовки в fallen-cards** теперь делает:

1. Читает сырые CSV (fallen/unclassified всех сессий).
2. Для каждой записи назначает ключи:
   - `unit_key` — по warunit через units*registry (сопоставление по dict_keys); не распознан → `unit_unknown*<hash>` + запись в журнал предложений.
   - `location_key` (место рождения, призыва) — через locations_dict (когда он появится в Astro-репо, сюда придёт его копия-только-для-чтения).
   - `burial_current_key` / `burial_primary_key` / `rebural_from_key` — через burials_current/primary + словарь объектов TASK-0010.
3. Строит frontmatter с ключами и slug `bitva-za-krym-1942-<document_id>` (детерминированный, как в v2; ФИО — только в title и H1, как вы и решили).
4. Отказные логи (нет ФИО / нет document_id) — как в v1/v2/v3.
5. Вывод: `data/cards/<document_id>.md` с ключами в frontmatter.

**Отчётный скрипт** `units-report.js` теперь не только частоты собирает, но и показывает: какие ключи уже выданы (`unit-655-sp-404-sd` есть в реестре Astro), какие — кандидаты на выдачу (новый полк встретился 12 раз).

**Словари в fallen-cards не живут.** Копии только для чтения — как зеркало реестра Astro для назначения ключей. Пополнение — в Astro-репо, и после пополнения Astro перегенерирует статику без участия fallen-cards.
