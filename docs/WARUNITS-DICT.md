# warunits_dict.json — регламент ключей и групп (WARUNITS-DICT v1)

Координата: `annachurasheva/fallen-cards` · `docs/WARUNITS_DICT.md` · v1 · 2026-10-09
Статус: единственная действующая логика ключа warunit во frontmatter.
Прежние решения (ключи unit-XXX, units_dict.json, любые нормализации) аннулированы.

## 1. Ключ

- Формат: `<NNN>-fallen-cards`; NNN — цифры с ведущими нулями до трёх знаков
  (001, 002, …; с 1000 — как есть).
- Ключ выдаётся группе ОДИН РАЗ И НАВСЕГДА: без перенумерации, без повторного
  использования номера, без переназначения другой группе.
- 001 присваивается самому массовому повтору на момент первичного наполнения.
  Каждая последующая новая группа получает следующий свободный номер
  в порядке создания.
- Ключ не зависит от изменения частот, слияний и новых прогонов.

## 2. Группа и варианты

- Группа — список вариантов: буквальные строки кириллицы и цифр ровно так,
  как они пришли из принятых CSV (регистр, знаки, пробелы внутри — как есть).
- Варианты группы однозначно указывают на одно войсковое подразделение.
  Пример: ["СКФ 826 сп 398 сд", "скф 398 сд 826 сп", "скф 826 полк 398 див.",
  "скф 826 сп 398 див."].
- Список вариантов только пополняется: свежие написания новых прогонов
  добавляются в группу решением оператора.
- Удаление варианта — только решением оператора с обязательной записью
  в note группы (история сохраняется).

## 3. Никаких нормализаций

- Совпадение = точное равенство строки поля warunit (как её извлёк парсер CSV;
  отрезка крайних пробелов — часть извлечения, не нормализация) одному из
  вариантов группы.
- Запрещено во всех слоях fallen-cards: нижний регистр, схлопывание пробелов,
  ё→е, транслит, удаление знаков и любые иные преобразования строк.
- Строка, отличающаяся хотя бы одним символом, — другое написание:
  новый вариант группы (решение оператора) или кандидат в новую группу.

## 4. Схема файла warunits_dict.json

{
  "_operator_note": { …выжимка настоящего регламента… },
  "groups": [
    {
      "key": "001-fallen-cards",
      "status": "active",
      "alias_of": null,
      "variants": ["276 сд"],
      "created_date": "2026-10-09",
      "created_frequency": 371,
      "sessions_seen": ["experts", "links_id_658_Арма-Эли"],
      "legacy_key": null,
      "note": null
    }
  ]
}

Поля:
- status: active | retired; retired — группа, поглощённая другой при слиянии.
- alias_of: у retired — ключ выжившей группы; у active — null.
- created_frequency: частота (уникальные document_id) на момент создания;
  исторический факт, не пересчитывается.
- legacy_key: необязательное; прежний ключ аннулированной системы unit-XXX
  (кросс-волк для Astro на время миграции).

## 5. Исправление ошибок разметки (без слияний и алиасов)

- У персоны одно место службы — последнее, на момент гибели. Значение warunit
  в CSV — факт этого места; иных «служб» не выводится и не подставляется.
- Две группы на одно подразделение — ошибка разметки, а не событие логики.
  До подтверждения ключа: оператор переносит варианты ошибочной группы
  в верную и удаляет ошибочную группу из файла; её номер не переиспользуется.
  После подтверждения ключа: ключ вечен, правка только списком variants
  (добавление/удаление с записью в note).
- Никаких retired, alias_of, косвенных ссылок и автопереносов в коде и файле.
- Перепись и отчёты ведутся ТОЛЬКО по буквальным строкам; любая нормализация
  (регистр, пробелы, ё→е) в отчётах запрещена. Прецедент: «276 сд | 371»
  старого отчёта — артефакт нормализации, не факт данных.

## 6. Назначение ключа во frontmatter

- generate-cards и любой иной слой fallen-cards: точное совпадение warunit
  с вариантом активной группы → unit_key: <NNN>-fallen-cards.
- Нет точного совпадения → unit_key: null; написание уходит в журнал
  кандидатов (частотная перепись). Скрипты НЕ создают группы и НЕ выдают
  ключи самопроизвольно.
- После выдачи группы оператором и пополнения вариантов перегенерация
  проставляет ключи; slug не меняется (slug-реестр).

## 7. Первичное наполнение и миграция (разовые)

- Частотная перепись: различные буквальные написания с частотами
  (уникальные document_id) по всем принятым CSV.
- Каждому различному написанию — предлагаемый номер по убыванию частоты
  (001 — самому массовому повтору).
- Ревью оператора: слияние написаний в группы (выживает предложенный номер
  выжившей группы), подтверждение.
- Миграция аннулированного unit_keys.json: каждая его запись становится
  группой; dict_keys переходят в variants; прежний ключ — в legacy_key;
  номер — по частоте переписи этих вариантов.
- После миграции unit_keys.json и units_dict.json — архив: скрипты их не читают.

## 8. Отчёты и черновики

- units-report: перепись буквальных написаний (без нормализаций и без
  статусов по архивным словарям); черновик предлагаемых ключей и слияний.
- Черновик не применяется автоматически; применение — решение оператора.
