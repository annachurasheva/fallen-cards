# warunits_dict.json — регламент ключей и групп (WARUNITS-DICT v1)

Координата: `annachurasheva/fallen-cards` · `docs/WARUNITS_DICT.md` · v1 · 2026-10-09
Статус: единственная действующая логика ключа warunit во frontmatter.
Прежние решения (ключи unit-XXX, units_dict.json, любые нормализации) аннулированы.

## 1. Ключ

- Формат: `<NNN>-fallen-cards`; NNN — цифры с ведущими нулями до трёх знаков
  (001, 002, …; с 1000 — как есть).
- Ключ выдаётся группе ОДИН РАЗ И НАВСЕГДА: без перенумерации, без повторного
  использования номера, без переназначения другой группе.
- 001 присваивается самому массовому повтору на момент первичного наполнения.
  Каждая последующая новая группа получает следующий свободный номер
  в порядке создания.
- Ключ не зависит от изменения частот, слияний и новых прогонов.

## 2. Группа и варианты

- Группа — список вариантов: буквальные строки кириллицы и цифр ровно так,
  как они пришли из принятых CSV (регистр, знаки, пробелы внутри — как есть).
- Варианты группы однозначно указывают на одно войсковое подразделение.
  Пример: ["СКФ 826 сп 398 сд", "скф 398 сд 826 сп", "скф 826 полк 398 див.",
  "скф 826 сп 398 див."].
- Список вариантов только пополняется: свежие написания новых прогонов
  добавляются в группу решением оператора.
- Удаление варианта — только решением оператора с обязательной записью
  в note группы (история сохраняется).

## 3. Никаких нормализаций

- Совпадение = точное равенство строки поля warunit (как её извлёк парсер CSV;
  отрезка крайних пробелов — часть извлечения, не нормализация) одному из
  вариантов группы.
- Запрещено во всех слоях fallen-cards: нижний регистр, схлопывание пробелов,
  ё→е, транслит, удаление знаков и любые иные преобразования строк.
- Строка, отличающаяся хотя бы одним символом, — другое написание:
  новый вариант группы (решение оператора) или кандидат в новую группу.

## 4. Схема файла warunits_dict.json

{
  "_operator_note": { …выжимка настоящего регламента… },
  "groups": [
    {
      "key": "001-fallen-cards",
      "status": "active",
      "alias_of": null,
      "variants": ["276 сд"],
      "created_date": "2026-10-09",
      "created_frequency": 371,
      "sessions_seen": ["experts", "links_id_658_Арма-Эли"],
      "legacy_key": null,
      "note": null
    }
  ]
}

Поля:
- status: active | retired; retired — группа, поглощённая другой при слиянии.
- alias_of: у retired — ключ выжившей группы; у active — null.
- created_frequency: частота (уникальные document_id) на момент создания;
  исторический факт, не пересчитывается.
- legacy_key: необязательное; прежний ключ аннулированной системы unit-XXX
  (кросс-волк для Astro на время миграции).

## 5. Исправление ошибок разметки (без слияний и алиасов)

- У персоны одно место службы — последнее, на момент гибели. Значение warunit
  в CSV — факт этого места; иных «служб» не выводится и не подставляется.
- Две группы на одно подразделение — ошибка разметки, а не событие логики.
  До подтверждения ключа: оператор переносит варианты ошибочной группы
  в верную и удаляет ошибочную группу из файла; её номер не переиспользуется.
  После подтверждения ключа: ключ вечен, правка только списком variants
  (добавление/удаление с записью в note).
- Никаких retired, alias_of, косвенных ссылок и автопереносов в коде и файле.
- Перепись и отчёты ведутся ТОЛЬКО по буквальным строкам; любая нормализация
  (регистр, пробелы, ё→е) в отчётах запрещена. Прецедент: «276 сд | 371»
  старого отчёта — артефакт нормализации, не факт данных.

## 6. Назначение ключа во frontmatter

- generate-cards и любой иной слой fallen-cards: точное совпадение warunit
  с вариантом активной группы → unit_key: <NNN>-fallen-cards.
- Нет точного совпадения → unit_key: null; написание уходит в журнал
  кандидатов (частотная перепись). Скрипты НЕ создают группы и НЕ выдают
  ключи самопроизвольно.
- После выдачи группы оператором и пополнения вариантов перегенерация
  проставляет ключи; slug не меняется (slug-реестр).

## 7. Первичное наполнение и миграция (разовые)

- Частотная перепись: различные буквальные написания с частотами
  (уникальные document_id) по всем принятым CSV.
- Каждому различному написанию — предлагаемый номер по убыванию частоты
  (001 — самому массовому повтору).
- Ревью оператора: слияние написаний в группы (выживает предложенный номер
  выжившей группы), подтверждение.
- Миграция аннулированного unit_keys.json: каждая его запись становится
  группой; dict_keys переходят в variants; прежний ключ — в legacy_key;
  номер — по частоте переписи этих вариантов.
- После миграции unit_keys.json и units_dict.json — архив: скрипты их не читают.

## 8. Отчёты и черновики

- units-report: перепись буквальных написаний (без нормализаций и без
  статусов по архивным словарям); черновик предлагаемых ключей и слияний.
- Черновик не применяется автоматически; применение — решение оператора.

# WARUNITS_DICT v2 — регламент словаря warunit

Координата: `annachurasheva/fallen-cards` · `docs/WARUNITS-DICT.md` · 2026-10-11.
Действующий регламент. При расхождении с более ранними записками (units-report,
draft1/draft2, unit_keys) приоритет — здесь и в `docs/ARCHITECTURE.md` §3.

## 1. Аннулированные тупики

Перечисленные ниже файлы **аннулированы** и перемещены
`scripts/clean-dictionaries.js` в `data/dictionaries/archive/` с префиксом
`deprecated-<метка>-`:

- `unit_keys.json` — реестр ключей `unit-*` (схема исчерпана);
- `units_dict.json` — словарь подмен «сокращение → полное название»;
- `units_registry.json` — реестр-предок;
- `unit_hierarchy.json` — картотека иерархии (операторская, скриптами не читалась);
- `warunits-draft1-*.md`, `warunits-draft2-*.md` — прежние черновики переписи.

Ни один скрипт конвейера не должен их читать. `scripts/parse-obd.js`,
`generate-cards.js` словари unit-* не трогают.

## 2. Формат ключей (решение оператора от 2026-10-11: семантические ключи)

Сквозная нумерация `001-fallen-cards … 145-fallen-cards` **АННУЛИРОВАНА** как
неинформативная. Действующее распределение — смысловое (семантическое),
привязанное к номеру дивизии и порядковому номеру подразделения в её составе.

- Ключи имеют **смысловой (семантический) формат**, а не сквозную нумерацию
  `001…145`.
- Узловая дивизия (группа без указания подразделения, только дивизия):
  формат строго `<NNN>-00-fallen-cards`, где NNN — номер дивизии
  (три цифры с ведущими нулями). Примеры: `390-00-fallen-cards`,
  `276-00-fallen-cards`, `077-00-fallen-cards`.
- Подразделение внутри дивизии: формат `<NNN>-<MM>-fallen-cards`, где MM —
  порядковый номер подразделения в перечне раздела `## Состав` файла дивизии
  `docs/TEXT/<NNN>-*.md` (нумерация с 01). Пример: 826-й сп — третий пункт
  `## Состав` 398-й сд → `398-03-fallen-cards`.
- Если состав подразделения в `docs/TEXT` не подтверждён (файл дивизии не найден
  или подразделения нет в `## Состав`), ключ равен `— (оператор)`; выдумывать
  ключ по смыслу запрещено.
- Иерархическая сверка: при противоречии написания и документа действует
  документ (`docs/TEXT`); перенос полка в другую дивизию по `validation_notes`
  картотеки `unit_hierarchy.json` — только решением оператора.
- Таблица `data/dictionaries/warunits-fallen-cards.md` сортируется по возрастанию
  колонки «Ключ»; строки `— (оператор)` идут в конец.

## 3. Конвейер (два скрипта, три артефакта)

### 3.1 build-warunits-dict.js — перепись с автослиянием

- Группировка по **буквальной** строке warunit (без trim, без toLowerCase).
- **Автослияние по набору чисел:** сигнатура строки = все числа (`/\d+/g`),
  отсортированные по возрастанию. Одинаковые сигнатуры сливаются в одну группу;
  выживает самая частая строка, проигравшие перечислены в `merged[]` с
  `merge_into` на proposed_key выжившей.
- Частота написания и группы — по **уникальным document_id**.
- Сортировка групп по убыванию частоты; временный черновик `proposed_key`
  (`001-fallen-cards`, `002-…`) служит только счётчиком строк переписи и
  **не является ключом словаря**: итоговые ключи — семантические, по §2
  (решение оператора от 2026-10-11). Стабильность нумерации черновика —
  перенос прежних proposed_key по совпадению строки из предыдущих draft3-json.
- Поля группы json: `proposed_key`, `key` (null до решения оператора),
  `merge_into` (null у выжившей), `variants`, `frequency`, `sessions`.
- Метка времени генерируется **один раз на прогон** и передаётся в оба писателя;
  при коллизии имени добавляется суффикс `-SS`. Запись атомарная: tmp → rename
  json+md подряд; сбой — пара не остаётся. **Перезапись запрещена**: существующие
  файлы не изменяются и не удаляются ни при каких условиях.
- md пишется **без фильтров, порогов и срезов**: число строк таблицы = число
  групп json, порядок и литералы идентичны.

### 3.2 build-warunits-table.js — механическая сборка активного словаря

- Источник строк: выбранный draft3-json (по умолчанию — самый поздний), все
  группы, порядок в json (сортировка итогового файла — по колонке «Ключ», §2).
- Четыре колонки (сверх не добавлять):
  1. ключ — семантический, по §2: `<NNN>-00-fallen-cards` (узловая дивизия) или
     `<NNN>-<MM>-fallen-cards` (подразделение, MM — порядковый номер в
     `## Состав` docs/TEXT); не подтверждён составом — `— (оператор)`;
  2. развёрнутое имя — **только из `docs/TEXT/*.md`** (front-matter `title`,
     пункт `## Состав`); нет подтверждения — `full_name` картотеки
     `unit_hierarchy.json`; нет и его — `— (оператор)`. Скрипт не выдумывает имена;
  3. написания — массив `variants` буквально, через «; »;
  4. адрес источника решений — путь к файлу `docs/TEXT/*.md` либо `source_doc`
     картотеки; нет источника — пустая ячейка.
- Разметка групп-химер (например «77 сд; 55 тбр», сигнатура [55,77]) — примечание
  «требует решения оператора», не развёрнутое имя.

## 4. Правила оператора

- Каждому group соответствует ровно один будущий `key`; присвоение ключа —
  решение Анны-Ch, в `key` пока null.
- Пустые сигнатуры (написания без чисел: «СКФ», «скф», «КрымФ») формально сливаются
  в одну группу — известное ограничение правила; при необходимости выносится
  правило «пустая сигнатура не сливается» решением оператора.
- Ручные слияния сверх автослияния запрещены; нормализации строк запрещены.

## 5. Регламент очистки

Перед каждым коммитом: `node scripts/clean-dictionaries.js`.

- Тупики → `data/dictionaries/archive/deprecated-<метка>-<файл>`
  (или удаление флагом `--delete`).
- Защищаются: всё с метками времени (`warunits-draft3-*`, `memorial_objects-*`),
  `plates_*.json`, `docs/`.
- **История проекта = файлы с метками времени.** Прошлые прогоны не перезаписываются
  и не удаляются; новый прогон — новая пара файлов.

## 6. Критерии воспроизведения

1. `node scripts/build-warunits-dict.js` создаёт пару json+md с одинаковой меткой;
2. `node scripts/build-warunits-table.js` создаёт/обновляет
   `warunits-fallen-cards.md`: строк таблицы = групп в json, колонка 1 уникальна,
   имён вне docs/TEXT нет;
3. повторный прогон через минуту даёт новую пару, старые файлы неизменны (md5);
4. `node scripts/clean-dictionaries.js` идемпотентен: второй запуск ничего не переносит.
